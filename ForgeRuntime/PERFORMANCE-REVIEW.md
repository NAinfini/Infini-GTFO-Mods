# 2.3.0 性能改动与同类实现对照

## 2.3.1 后续改动（未部署／未取得实机性能对比）

下方表格是 2.3.0 的历史实现对照。2.3.1 已按该表的差距继续修改：发现候选不再是玩家×全注册表，而是每名存活玩家每 0.25 秒执行 4 米附近碰撞查询；复用结果数组、按对象去重，数组满时扩容重查。终端／设备通过登记的实体父级定位，交互和拾取事件仍保留。新增 `marker_spatial` 记录查询数、命中碰撞体数和缓冲扩容；密集场景与动态设备发现仍需原生实测，不能仅凭较少遍历给双方排名。

ResourceHelper 的近距／注视展开已接入，增加最小注视角和 0.2 秒离焦延迟。详情变化只切原生显示标志，不重复重设样式。补给 HUD 使用独立原生文字和类别图标，透明度不再作用于整个队友标记；没有增加普通背包清单或终端使用者信息。

诊断新增每条已计时路径的 `managed_allocated_bytes` 与 `maximum_managed_allocated_bytes`，并把 HUD 显示、放置预览和终端维护分别计时。它们是当前线程托管累计分配／单次最大值，不是存活内存、原生分配或 GPU 耗时；嵌套路径不能相加。报告解析已增加对应输出和边界测试。原生 FrameTiming／sampler 缺口没有因此解决。

## 2.3.0 基准记录

2026-09-08。基准实测来自 2.2.7 的 R4B3 日志 `InfiniTweaks_Performance_20260908_163013.log`；2.3.0 是本地候选构建，尚未部署和实机复测。本文不将代码分析、离线测试写成 FPS 提升。

## 已有证据与本次范围

标记是已计时 Infini 路径中最明显的持续成本：前段平均 0.406 ms/帧，后段 2.457 ms/帧，最大一次 42.567 ms。旧日志没有每次对象数量和内部步骤，不能断言增长全部来自标记数量，也不能用它解释全部 120→40 FPS 的下降。120 FPS 的整帧预算为 8.33 ms，40 FPS 为 25 ms。

诊断扫描总 CPU 5918.1 ms，最大执行片段 592.863 ms，分布在 34.12 秒。总耗时不是一次连续卡住，但最大片段足以成为开局卡顿调查重点。它不能解释扫描完成后的整局持续低帧。

本轮只优化这两条已测路径及其诊断信息。没有修改 ReplayRecorder、画质、其他插件、已安装 DLL 或玩家奖励设置。录制器 7.56 GiB 是累计分配，不是同时占用；其分配热点仍待单独调查。

## 实现及诊断变化

- `MarkerPresentation` 集中拥有自家克隆标记的提交状态；样式变化可能覆盖原生默认值，因此重申标题、颜色、大小、透明度及可见性。隐藏/恢复和实时配置变化保留，未禁用原生位置跟踪。
- `ItemMarkers` 新增 `MarkerDiscovery`、`MarkerRefresh` 子计时，以及 `marker_summary` 的记忆数、范围内数、已分配标记数、注册对象数、发现检查/射线次数、标题检查/实际变化组数。变化组不是 draw call，也不包含全部原生更新；两个子计时嵌套于 ItemMarkers，不能重复相加。
- `SceneInventory` 在对象和组件边界让出执行权，每个场景对象只查询一次组件，按原生类型继承关系分类；分类结果按类缓存。范围为已加载场景及诊断对象所在持久场景，包括非激活对象，不含未挂到场景的 prefab 组件。纹理、网格、材质、音频资产仍用原生全局清单。新旧组件数量统计范围不同，不能直接将减少解释为游戏对象被删除。
- 原生资产枚举记录 `asset_enumeration` 耗时；扫描阶段记录起止，超 2 ms 的不可拆分执行片段记录 `asset_slow_step`。2 ms 是协作式预算，不是硬上限：根对象枚举、单对象组件查询、资产枚举等调用仍不能中途暂停。扫描期间世界会变化，清单不是原子快照。
- 原生 sampler 在启动无名称时，每次进入关卡补试一次；已有 Profiler 开启状态只记录、不接管，并明确其所有者未知。报告解析器支持新字段，也明确指出旧日志缺少标记数量证据。

## CPU/GPU 采集边界仍在

实测游戏为 Unity 2019.4.21f1 / DX11；旧日志确认 FrameTiming 原生类缺失、CPU/GPU 帧样本 0/0、sampler 为 0。Unity 后续才宣布新增 Frame Timing Manager 的 DX11 支持，不能把新版本引擎的示例直接套在此游戏上。[Unity 官方说明](https://discussions.unity.com/t/update-for-frame-timing-manager/860718)

因此此候选没有声称修复所有原生采集缺口，更没有逐皮肤/材质/物件的精确 CPU/GPU 毫秒归因。资产数量、大小、阴影和绘制相关状态是工作量线索，不等于独立耗时。若零样本持续，需另行取得兼容此发行版的外部原生采集，才能确认 CPU/GPU 瓶颈；不要把缺失显示为零开销。

## 已执行验证

- Release 编译、781 项主回归断言、87 项游戏接口契约、5 项日志解析测试通过；契约检查不执行 IL2CPP detour。
- 独立场景遍历测试 8 项通过：502 个对象、500 层子对象链、派生类型归类、持久场景去重，2005 次可让出执行边界，每对象一次组件查询。测试项目单独输出，避免与主回归入口混用。
- 单标记保持不变连续调用 7200 次：旧路径四个属性 setter 共 28800 次，新路径初始化后为 0 次。该结果仅是托管测试中的调用次数，不是实际 CPU、GPU、draw call 或 FPS 测量。

## 实机对照方法与验收

1. 退出 GTFO 后部署候选；确认新日志版本为 2.3.0。暂不同时启用两个标记提供者。沿用同分辨率、画质、队伍、R4B3 路线、发现数量和录制器开关；分别记录开局及较长时间后的同类片段。
2. 先比较 ItemMarkers 毫秒/帧和毫秒/调用、发现/刷新子计时、注册/记忆/分配数量、实际 UI 变化组；核对扫描总耗时、最大执行片段及阶段。平均帧率用帧数/总帧时间，不能平均 FPS 样本代替。
3. 对照上游时匹配共同功能和范围；无法匹配的名称折叠/透明度等单列。录制器开关只作独立控制变量，不能同时改变多个设置后将收益全部归给标记。
4. 正确性先过关：补给包/消耗品拿起消失、放回重现；箱柜和普通门不标；终端和设备发现；cryo/电池随队友、跨维度、放下、完成；临时 ping 不重复；瞄准/菜单即时隐藏；图标/数量/颜色更新；检查点后恢复。10 Hz 非事件状态检查允许最多约 100 ms 延迟，位置跟踪仍由原生每帧处理。

只有这些检查和同条件新日志支持，才能认定“整体更快且功能不退步”。目前已完成源码优化与离线验证，尚无新的实机性能结论。
